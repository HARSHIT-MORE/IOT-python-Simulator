# IoT Simulator Review and Validation Notes

## Scope

This review preserves the existing Adaptive Resource-Aware Zero-Trust IoT architecture and the current trust, risk, resource, and decision thresholds except where the code's classification logic was demonstrably misleading. The ESP32 firmware was not changed.

## Changes made

1. **Gateway HMAC verification (`gateway/gateway.py`)**
   - For MQTT observations, verify the original `raw_payload` using `verify_hmac_raw_payload()` rather than serializing the adapter-enriched `raw_data` dictionary.
   - Keep the legacy canonical-JSON path only for callers that do not provide the original MQTT text.
   - A failed or missing device-origin HMAC still results in DENY regardless of trust score.
   - Missing behavior/context scores in the authentication-failure evidence path now default to neutral values rather than falsely implying highly abnormal behavior/context.

2. **MQTT adapter (`iot/mqtt_adapter.py`)**
   - Preserve the original raw MQTT JSON text.
   - Update trusted sequence/message replay state only after the device-origin HMAC verifies successfully. Invalid or unsigned messages can still be passed to the gateway for denial/evidence, but cannot advance the trusted sequence state and poison later legitimate messages.

3. **Startup and decision consistency (`main.py`)**
   - Startup waits for HMAC-verified observations from all expected devices; an unsigned publisher cannot satisfy readiness merely by claiming an expected device ID.
   - Missing/failed HMAC explicitly overrides a trust-score ALLOW in the displayed decision path; the gateway independently enforces the same denial.
   - Integrate `ExperimentVisualizer` so a live run writes round-by-round diagnostic plots and CSV. Live data is labelled `LIVE_UNLABELLED`; it is not treated as attack ground truth.
   - Clarify that fixed recovery scores are synthetic demonstration inputs, not measured post-remediation values.

4. **Clock anomaly handling (`security/device_attack_detector.py`)**
   - An unsigned time-of-day-only message with no device epoch is not labelled `CLOCK_DRIFT`, because date/timezone cannot be authenticated. The message remains unverified and is rejected by the gateway.
   - A supplied but invalid HMAC is an integrity/authentication failure, but is not alone treated as proof of attacker intent.
   - The existing 120-second epoch drift threshold remains unchanged and should be calibrated with normal device traces.

5. **Forensic classification/counting (`security/forensic_analyzer.py`, `gateway/history_manager.py`)**
   - Carry an explicit `confirmed_attack` flag in forensic results.
   - Count a confirmed incident only when the forensic pipeline explicitly marks an attack confirmed; severity or the mere presence of an indicator is not sufficient.
   - Explicitly confirmed tampering takes precedence over the generic failed-HMAC label; failed HMAC alone remains suspected tampering.

6. **Tests**
   - Corrected the stale test import from `mqtt_adapter_fixed` to `iot.mqtt_adapter`.
   - Added tests for exact raw-payload preservation, adapter-to-gateway HMAC verification, altered payload rejection, invalid-signature sequence poisoning, clock fallback handling, forensic confirmation counts, trust equations, adaptive weights, and RCF/resource-pressure calculations.

## Findings that still need controlled experiments

- **Temperature-rate rule:** the observed 24.0°C to 66.4°C change is a 42.4°C step and correctly triggers the current `5.0°C per accepted sample` heuristic. It is not, by itself, proof of an attack. Consider elapsed-time-normalized rate detection and calibrate using normal traces and known simulator changes before changing the threshold.
- **Isolation policy:** a failed HMAC rejects that message but does not automatically isolate the device. Logical isolation is applied when the decision engine explicitly requires it. This conservative separation is intentional for now; if repeated failures should trigger isolation, define and test a threshold separately.
- **Recovery:** recovery requires a device to be logically isolated first. Synthetic post-remediation scores are demonstrations only. Use measured/authenticated values before claiming recovery success in research results.
- **Trust/risk calibration:** trust and risk outputs are weighted heuristics, not calibrated probabilities. In particular, final risk is `probability_of_compromise × impact`, so low-impact devices can have low risk even with a telemetry anomaly. Validate thresholds and report this limitation.
- **Resource telemetry:** current ESP32 firmware does not report CPU, RAM, battery, or bandwidth telemetry. RCF and resource pressure are currently calculated from the Python device model, not measured ESP32 hardware metrics. The security-level labels do not switch HMAC to a different cryptographic algorithm; HMAC verification remains mandatory for every signed message.
- **Evaluation metrics:** precision, recall, false-positive rate, and false-negative rate must remain unavailable until each observation has an independent attack-ground-truth label. The live plotting label `LIVE_UNLABELLED` is descriptive only.
- **Replay and deployment security:** the public test MQTT broker, topic, and demo keys are for simulation only. The sequence-state fix prevents invalid signatures from poisoning the trusted counter, but stale valid messages across boot IDs still need an explicit signed-timestamp freshness/replay policy. Do not use the demo keys or public broker for production.
- **Camera scope:** `CAMERA_001` publishes camera-like metadata only; it does not send actual image frames.

## Recommended live validation sequence

1. Open the Wokwi project and ensure all four devices are publishing: `CLOCK_001`, `TEMP_001`, `MOTION_001`, and `CAMERA_001`.
2. Confirm each device has NTP time available so the firmware can include `device_timestamp_epoch` and generate an HMAC.
3. From this project directory, run `python main.py`.
4. Confirm startup waits until all four devices provide HMAC-verified messages.
5. Confirm normal signed messages show adapter verification and gateway verification success. The first unsigned/modified message should be denied; it must not be counted as confirmed tampering without independent evidence.
6. Run a baseline without injected changes, then separate controlled experiments for message modification, stale/replayed payloads, clock drift, and temperature changes. Record ground-truth labels independently from the detector.
7. Compare fixed-weight and adaptive-weight runs, repeat each scenario, and only then report detection metrics, resource overhead, and latency.
8. Use the freshly generated plots/CSV from `experiments/results/`; do not reuse historical plots as evidence of the patched run.
